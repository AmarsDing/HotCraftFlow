## 1. 系统上下文

```
① IC ──mm.intel.normalized.v1 (IntelItem)──►
                                              ┌────────────────────────────────┐
                                              │  ② TT 热点追踪系统              │
                                              │                                │
                                              │  话题聚类 → 时序写入 → 归一化   │
                                              │  → 生命周期 → 突发 → 选题评分   │
                                              └───┬──────────┬──────────┬─────┘
                                                  │          │          │
                    TopicCandidate(route=mme) ────┘          │          └──── Alert
                              ▼                              │                 ▼
                        ④ MME 加工             TopicCandidate(route=mia)   推送渠道
                                                    ▼                    (Webhook/站内/
                                              ③ MIA 分析                  邮件/企业微信)

⑤ MAP ──mm.map.feedback.v1 (PerformanceSnapshot)──► ② TT（FR-TRK-13 回流校正）
```

**边界原则**：TT **只做量化追踪与排序**，不做内容加工（MME 的活）、不做市场判断（MIA 的活）。

## 2. 分层架构

```
┌─ L1 接入层  Ingest ────────────────────────────────────────────┐
│  订阅 mm.intel.normalized.v1                                   │
│  话题聚类（与 IC 的 cluster_id 协同但独立判定）                  │
│  构造 (topic, platform, t) 快照点                               │
└──────────────────────────┬────────────────────────────────────┘
                           ▼
┌─ L2 时序层  TimeSeries ────────────────────────────────────────┐
│  InfluxDB 2.x  measurement: topic_heat                         │
│  tags: topic_id / platform / region / category                 │
│  fields: rank / heat_score / views / likes / comments / eng_rate│
│  降采样：raw 90d → 5m 聚合 1y                                   │
└──────────────────────────┬────────────────────────────────────┘
                           ▼
┌─ L3 计算层  Analytics ─────────────────────────────────────────┐
│  ① 归一化（rank_pct / eng_pct / freshness / breadth → heat）    │
│  ② 动态指标（velocity / accel，EWMA 平滑）                      │
│  ③ 生命周期判定（五阶段状态机）                                  │
│  ④ 突发检测（三方法投票）                                        │
└──────────────────────────┬────────────────────────────────────┘
                           ▼
┌─ L4 决策层  Decision ──────────────────────────────────────────┐
│  选题评分（hot × freshness × workability × compliance）         │
│  路由判定（route = mme / mia / both）                           │
│  产出 TopicCandidate                                           │
└──────────────────────────┬────────────────────────────────────┘
                           ▼
┌─ L5 出口层  Delivery ──────────────────────────────────────────┐
│  Alert 推送（多渠道）· 看板 API · 订阅管理 · 热点档案            │
└────────────────────────────────────────────────────────────────┘
```

## 3. 模块划分（Go 包结构）

```
apps/server/
  api/media/v1/tt/
    topic.proto          # 话题、聚类、订阅
    trend.proto          # 时序查询、阶段、突发
    alert.proto          # 告警、推送渠道、静音
  app/admin/internal/
    biz/tt/
      ingest_usecase.go      # 消费 IntelItem → 快照点
      cluster.go             # 话题聚类与人工干预
      normalize.go           # 三层热度归一化（核心算法）
      dynamics.go            # velocity / accel（EWMA）
      lifecycle.go           # 五阶段状态机
      burst.go               # 三方法投票
      scoring.go             # 选题评分与路由
      alert_usecase.go       # 告警生成与推送
      ports.go               # TimeSeries / Notifier / Weights 端口
    data/tt/
      topic_repo.go          # PG：话题/订阅/选题/告警
      influx.go              # InfluxDB 读写客户端（TimeSeries 端口实现）
      cache.go               # Redis：权重、热话题缓存、静音表
    service/tt/
    worker/tt/
      schedule.go            # asynq：周期计算、降采样、档案归档
```

### 3.1 职责表

| 模块 | 职责 | 不做 |
|------|------|------|
| `biz/tt/normalize.go` | 三层热度计算，**输出因子明细** | 不写存储 |
| `biz/tt/dynamics.go` | EWMA 平滑与导数 | 不判阶段（只提供数值） |
| `biz/tt/lifecycle.go` | 阶段状态机 | 不算分（只消费数值） |
| `biz/tt/burst.go` | 三方法投票 | 不推送（交给 alert_usecase） |
| `biz/tt/scoring.go` | 选题评分 + 路由判定 | 不自动采纳 |
| `data/tt/influx.go` | **唯一** InfluxDB 接触面 | 不含业务逻辑 |

## 4. 关键数据流

### 4.1 主链路（每采集周期）

```
mm.intel.normalized.v1 (IntelItem)
  → ingest_usecase
     → 话题聚类：按 cluster_id + 语义相似度 → topic_id（新建或归入）
     → 构造快照点 → 写 InfluxDB（幂等：同 key 覆盖）
     → 发 mm.trend.snapshot.v1（内部）
  → analytics（周期或触发式）
     → normalize.run(topic) → heat_score + factors
     → dynamics.run(topic) → velocity / accel
     → lifecycle.eval(topic) → stage + stage_evidence
     → burst.detect(topic)
        ├─ 命中 ≥2 方法 → 生成 Alert → mm.trend.burst.v1 → 推送
        └─ 未命中 → 静默
  → scoring（每 15 分钟 / 触发式）
     → 对 rising / peak 阶段话题打分 → TopicCandidate
     → 按 route 发 mm.trend.candidate.v1
```

### 4.2 订阅追踪（FR-TRK-06）

```
用户创建订阅（关键词 / 话题 / 平台组合）
  → 落 TrendSubscription 表
  → 订阅存在时：即使话题不在热榜，也**主动采集**该关键词
     （向 IC 发回采请求，或由 TT 直采，取决于 IC 是否支持该信源）
  → 曲线持续更新
  → 取消订阅 → 停止主动采集（已有时序数据保留）
```

> **设计约束**：订阅的主动采集必须**经由 IC**，不得由 TT 直接发 HTTP——否则会绕过 IC 的合规闸门与速率治理。

### 4.3 回流校正（FR-TRK-13，P2）

```
⑤ MAP 发 mm.map.feedback.v1 (PerformanceSnapshot)
  → TT 订阅
  → 关联 candidate_id → 计算「预测热度 vs 实际表现」偏差
  → 累积样本 → 周期性建议权重调整（**不自动改权重**，出建议报告）
  → 人工确认 → 更新 heat 权重
```

> **重要**：权重调整**不全自动**。自动改权重会造成热度分口径漂移，历史数据不可比。

### 4.4 降级路径（InfluxDB 不可用）

```
写入失败 → 落 Redis 缓冲队列（TTL 1h）+ 指标告警
查询失败 → 看板返回「最近 N 点内存态」+ 明确提示「时序库不可用，数据不完整」
           **禁止**静默返回空结果
```

## 5. 外部依赖与部署形态

| 依赖 | 形态 | 部署位置 | 失败影响 | 回退 |
|------|------|---------|---------|------|
| **InfluxDB 2.x** | 独立服务 | 本机 `D:/influxdb2-2.9.1-windows_amd64`（**需确认可复用**） | 时序不可用 | Redis 缓冲 1h + 降级提示 |
| NATS JetStream | 基础设施 | 本机 | 上游断流 | 本地磁盘队列 ≤1h |
| PostgreSQL | 基础设施 | 本机 `:5434` | 元数据不可写 | 无（强依赖） |
| Redis | 基础设施 | 本机 `:6380` | 缓存降级为进程内 | 可接受 |
| **① IC** | 上游系统 | 同进程不同模块 | **无数据** | 无（强依赖） |

> **InfluxDB 选型说明**：本机已有 2.9.1，可直接复用，省去新组件引入。备选 TimescaleDB（PG 扩展，运维更简单但需 PG 插件）。

## 6. 接口契约

### 6.1 NATS

| Subject | 载荷 | 方向 |
|---------|------|------|
| `mm.intel.normalized.v1` | `IntelItem` | ← IC |
| `mm.trend.snapshot.v1` | 内部结构（快照点） | 内部 |

| `mm.map.feedback.v1` | `PerformanceSnapshot` | ← MAP（P2） |

### 6.2 REST（`api/media/v1/tt`）

| 方法 | 路径 | 用途 |
|------|------|------|
| `GET` | `/api/v1/media/tt/topics` | 话题列表（阶段/热度筛选排序） |
| `GET` | `/api/v1/media/tt/topics/{id}` | 话题详情（含阶段与因子数值） |
| `GET` | `/api/v1/media/tt/topics/{id}/series` | 完整时序（分页，查 InfluxDB） |
| `POST` | `/api/v1/media/tt/topics/{id}/merge` | 人工合并话题 |
| `POST` | `/api/v1/media/tt/topics/{id}/split` | 人工拆分子话题 |
| `GET/POST` | `/api/v1/media/tt/subscriptions` | 订阅管理（FR-TRK-06） |
| `GET` | `/api/v1/media/tt/candidates` | **选题台**（FR-TRK-09，核心 UI） |
| `POST` | `/api/v1/media/tt/candidates/{id}/adopt` | 采纳 → 触发 MME/MIA |
| `POST` | `/api/v1/media/tt/candidates/{id}/reject` | 驳回（须填原因） |

| `GET` | `/api/v1/media/tt/alerts` | 告警列表 |
| `POST` | `/api/v1/media/tt/alerts/{id}/ack` / `mute` | 确认 / 静音 |
| `GET` | `/api/v1/media/tt/weights` · `PATCH` | 热度权重查看与配置 |
| `GET` | `/api/v1/media/tt/archive` | 热点档案（P2，按日期） |

### 6.3 前端页面（Quasar）

| 路由 | 页面 | 内容 |
|------|------|------|
| `/media/tt/candidates` | **选题台**（核心） | 排序卡片列表、四维分数条、路由标记、采纳/驳回/稍后 |
| `/media/tt/topics/{id}` | 话题详情 | 热度曲线（多平台叠加）、阶段标注、**因子数值面板**、溯源信息 |
| `/media/tt/dashboard` | 热点看板 | 实时热点榜、阶段分布、跨平台对比 |
| `/media/tt/subscriptions` | 订阅管理 | 增删改订阅、曲线预览 |
| `/media/tt/alerts` | 告警中心 | 告警列表、依据展开、静音管理 |

**UI 强制要求**：热度分数旁**必须**提供「为什么是这个分」的入口，展开显示四因子取值（NFR-TT-05）。

## 7. 关键技术决策（ADR 摘要）

| # | 决策 | 备选 | 理由 |
|---|------|------|------|
| **ADR-TT-01** | 时序用 **InfluxDB 2.x**，元数据用 PostgreSQL | 全 PG（TimescaleDB） | 本机已有 InfluxDB 2.9.1，省去新组件；写入吞吐与降采样能力现成 |
| **ADR-TT-02** | 话题聚类**独立判定**，不直接复用 IC 的 `cluster_id` | 直接用 IC cluster | IC cluster 服务于「去重」，TT topic 服务于「演化追踪」，粒度与目标不同；但 IC cluster_id 作为**强特征**输入 |
| **ADR-TT-03** | 热度权重**可配且显式暴露因子** | 黑箱模型 | NFR-TT-05 可解释性是硬要求；模型黑箱不可接受 |
| **ADR-TT-04** | 突发检测用**三方法投票**而非单一算法 | 只用 Z-score | 单一方法在低基数/榜单型数据上误报高；投票可互相印证 |
| **ADR-TT-05** | 回流权重**出建议不自动改** | 自动调权重 | 自动改会造成历史热度分口径漂移，跨时间不可比 |
| **ADR-TT-06** | 订阅的主动采集**必须经 IC** | TT 直采 | 否则绕过 IC 的合规闸门与速率治理（架构红线） |
| **ADR-TT-07** | 采样默认 **30 分钟** | 5 分钟 | newsnow 默认缓存 30 分钟，更高频率**无意义**且增上游负载（NFR-TT-04） |
| **ADR-TT-08** | 时区**存 UTC 展示上海** | 存本地时间 | 财经跨市场对齐硬要求（NFR-TT-03） |

## 8. 容量与性能估算（V1 单实例）

| 项 | 估算 |
|----|------|
| 活跃话题数 | 2,000–8,000 |
| 采样频率 | 热榜 30 分钟（48 点/日/话题） |
| 日增点 | 约 10–40 万点 |
| InfluxDB 90 天容量 | 约 3,600 万点，估算 2–5 GB（压缩后） |
| 计算频率 | 归一化/动态：每采样点触发；突发：每点；选题评分：15 分钟 |
| 查询 QPS | 看板峰值 ≤20 |

## 9. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 热度权重初期标定不准 | 排序不符合直觉，选题台价值下降 | ① 因子显式可查；② 提供权重配置页；③ FR-TRK-13 回流校正闭环 |
| InfluxDB 单点故障 | 看板不可用 | Redis 缓冲 + 降级提示；考虑后续主从 |
| 话题聚类错误 | 不同事件被并成一个话题 | 人工拆分 + 反馈样本；阈值可配 |
| 突发误报过多 | 推送疲劳，用户关掉告警 | 三方法投票 + 静音 + 误报标记调参 |
| 采样点缺失 | 曲线断裂，判定失真 | 缺失率指标监控（目标 <2%）；插值需**显式标注**为插值点 |
| 时区处理错误 | 财经时间序列错位 | 单一工具函数封装，单元测试覆盖夏令时/跨日场景 |

## 10. 与其他子系统的接口约定

| 对 | 约定 |
|----|------|
| ← **① IC** | 消费全量 `IntelItem`。依赖 `metrics._as_of` 判断快照新鲜度；`dedup.cluster_id` 作为聚类**强特征** |
| → **④ MME** | 发 `TopicCandidate`（`route=mme`）。MME 依赖 `material_refs` 与 `suggested_angles` |
| → **③ MIA** | 发 `TopicCandidate`（`route=mia`）。MIA 依赖 `topic_id` 关联 `ImpactCard` |
| → 推送 | 发 `Alert`。**必须**含 `methods_hit` 与各方法数值 |
| ← **⑤ MAP** | 消费 `PerformanceSnapshot` 做权重校正建议（P2） |

**纪律**：TT **不反向要求** IC 增加仅自己需要的字段。走契约演进流程（共享文档 §9）。
