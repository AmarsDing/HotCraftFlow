## 3. 关键设计：矩阵展开（★ 本增量的核心）

### 3.1 三维度展开模型

```
输入：一个素材源（asset_id）+ 用户确认的切点（EDL）
                │
    ┌───────────┼───────────┐
    ▼           ▼           ▼
 B 内容矩阵   A 平台矩阵   C 变体矩阵
（N 个选题） （3 种画幅） （M 个 Hook/封面）
    └───────────┼───────────┘
                │ 笛卡尔积
                ▼
        N × 3 × M 个 Variant
        装入一个 VariantSet
```

### 3.2 为什么「展开计划」与「渲染」分离

```
MatrixExpand 阶段：生成 VariantSet 计划（纯元数据，秒级）
   → 用户在审核台看到 N×3×M 的网格
   → 用户**可删减**（去掉不想要的组合）★ 关键
Render 阶段：只对**保留的组合**渲染（分钟级～小时级）
```

**理由**：30 个变体全渲染要很久，用户很可能只想保留 12 个。**先展开后渲染、允许删减**，能显著节省算力与时间。

### 3.3 变体命名与组织

```
VariantSet vs_01J...
  ├── v_01J...  9:16  hook_a  cover_1  「高光1」
  ├── v_01J...  1:1   hook_a  cover_1  「高光1」
  ├── v_01J...  16:9  hook_a  cover_1  「高光1」
  ├── v_01J...  9:16  hook_b  cover_2  「高光1」
  └── ...
```

**分组维度**（前端网格可按任一维度聚合）：内容版本 / 画幅 / Hook / 平台。

## 4. 关键设计：产物缓存（FR-MIX-02）

### 4.1 缓存层次

| 层 | 缓存对象 | Key | 复用场景 |
|----|---------|-----|---------|
| **L1 素材** | 下载产物 | `asset_id` / URL 指纹 | 同一素材多次建任务 |
| **L2 转写** | ASR 结果（SRT/VTT） | `asset_id` + ASR 引擎 + 语言 | 二次成片**不重跑 ASR** |
| **L3 理解** | 章节/要点/报告/关键帧 | `asset_id` + 分析版本 + intent 哈希 | 二次成片**不重跑 LLM** |
| **L4 渲染中间** | reframe 后的中间片 | `asset_id` + 切点 + 画幅 | 换 Hook 不重做 reframe |

### 4.2 缓存失效

```
失效条件（任一）：
  ① asset 内容变更（指纹不匹配）
  ② 分析提示词版本变更（prompt_version 变化）
  ③ 用户显式指定 force_refresh
  ④ 缓存 TTL 到期（默认 90 天）
```

> **验收判据**：二次成片时 ASR/LLM 调用次数为 **0**（需求验收 §7-3）。

## 5. 关键设计：多画幅渲染（FR-MIX-03）

### 5.1 画幅规格表

| 画幅 | 分辨率 | 目标平台 | reframing 策略 |
|------|--------|---------|---------------|
| **9:16** | 1080×1920 | 抖音 / TikTok / Shorts / Reels | 主体追踪裁切（有 GPU 优于无 GPU） |
| **1:1** | 1080×1080 | 小红书 / IG | 中心裁切 + 轻微主体偏移 |
| **16:9** | 1920×1080 | B站 / YouTube | 原画幅直通（无裁切） |

### 5.2 字幕安全区

| 画幅 | 底部安全区 | 顶部安全区 | 说明 |
|------|-----------|-----------|------|
| 9:16 | ≥380px | ≥130px | 避开抖音右侧互动栏与底部文案 |
| 1:1 | ≥180px | ≥100px | |
| 16:9 | ≥120px | ≥80px | |

> **NFR**：字幕**不得**句中硬切（既有 PRD 0.8 风险项）；安全区违规在质检中判 `subtitle_ok=false`。

### 5.3 渲染调度

```
渲染任务队列（asynq）
  并发控制：默认 2（CPU 密集，避免打满）
  优先级：用户显式请求 > 批量后台
  断点重试：失败保留中间产物（NFR-MME-08）
  进度上报：每个变体的进度与预估剩余时间（避免用户以为卡死）
```

## 6. 关键设计：差异化度检查（FR-MIX-05）🔴

> **这不是可选功能，是合规风控措施。**

### 6.1 检查维度

| 维度 | 方法 | 阈值 |
|------|------|------|
| **视觉** | 关键帧 pHash 序列相似度 | ≥0.90 告警 |
| **Hook** | 前 3s 视频+音频指纹 | ≥0.85 告警 |
| **文案** | 标题/简介 SimHash | ≥0.92 告警 |
| **音频** | 音频指纹（可选） | ≥0.95 告警 |

### 6.2 处置

```
两两计算 → min_pair_similarity 落入 VariantSet.diff_check
  warn = false：正常
  warn = true ：UI 高亮该对变体，提示「建议改 Hook / 封面 / 开头」

**不阻断**送审（差异化度是风险提示，不是硬性质量门禁）
但**必须**在审核台可见——审核人需看到该提示才能决策
```

> **设计权衡**：差异化度过低主要风险是**平台查重判定为搬运**，属运营风险而非内容违规。故设计为**强提示 + 人工决策**，而非硬阻断。这与「合规闸门」（硬阻断）不同。

## 7. 模块划分（Go 包结构）

```
apps/server/
  api/media/v1/mme/
    task.proto            # 加工任务、素材、分析结果
    variant.proto         # VariantSet / Variant、审核、差异化检查
    render.proto          # 渲染任务、进度、重渲
  app/admin/internal/
    biz/mme/
      task_usecase.go         # 任务编排（M2→M3→M4→M5）
      asset_dedup.go          # FR-MIX-07 素材去重与引用计数
      analysis_cache.go       # FR-MIX-02 产物缓存
      copy_variant.go         # FR-MIX-04 平台文案差异化
      matrix_expand.go        # ★ 三维展开
      render_planner.go       # 渲染计划与调度
      diff_check.go           # FR-MIX-05 差异化度
      qc.go                   # 渲染自检
      template_usecase.go     # FR-MIX-08 混剪模板
      variant_set_usecase.go  # VariantSet 组装与送审
      ports.go                # Downloader / ASR / LLM / Renderer / Storage 端口
    data/mme/
      task_repo.go            # MontageTask / Asset
      variant_repo.go         # VariantSet / Variant
      cache_repo.go           # 产物缓存（Redis 索引 + 对象存储）
      storage.go              # 媒体文件存储
    service/mme/
    worker/mme/
      render_worker.go        # asynq 渲染消费者（并发控制）
      cache_gc.go             # 缓存清理
```

### 7.1 职责表

| 模块 | 职责 | 不做 |
|------|------|------|
| `biz/mme/matrix_expand.go` | 生成变体**计划** | 不渲染 |
| `biz/mme/render_planner.go` | 渲染任务调度与并发 | 不执行 FFmpeg（调 port） |
| `biz/mme/diff_check.go` | 相似度计算与告警 | 不阻断送审 |
| `biz/mme/qc.go` | 渲染自检，**硬门禁** | 不做内容价值判断 |
| `data/mme/storage.go` | **唯一**媒体文件接触面 | 不含业务逻辑 |

> ⚠️ **说明**：MME 是五个子系统中**唯一大量依赖本机 FFmpeg / Python 侧车**的，部分能力（渲染、剪映草稿）以**侧车进程 + CLI** 形态存在，不全部是 Go 实现。这是既有 MVP 0.8 的既定架构，本设计沿用。

## 9. 关键技术决策（ADR 摘要）

| # | 决策 | 备选 | 理由 |
|---|------|------|------|
| **ADR-MME-01** | **先展开后渲染**，允许删减 | 展开即全渲染 | 30 个变体全渲浪费算力；用户通常只保留一部分 |
| **ADR-MME-02** | 变体簇 `VariantSet` 作为统一管理单元 | 散装文件 | 矩阵规模下无容器无法管理 |
| **ADR-MME-03** | 分析产物**四级缓存** | 每次重跑 | ASR/LLM 是最贵环节；复用是刚需（NFR-MME-02） |
| **ADR-MME-04** | 差异化检查**强提示不硬阻断** | 硬阻断 | 主要风险是平台查重（运营风险），非内容违规；交人工决策 |
| **ADR-MME-05** | 渲染**并发默认 2** | 高并发 | CPU 密集；打满会导致整台机器无响应 |
| **ADR-MME-06** | 渲染/剪映走**侧车进程 + CLI** | 全 Go 实现 | 既有 MVP 0.8 既定架构；FFmpeg/pyJianYingDraft 生态在 Python |
| **ADR-MME-07** | MME **不实现发布** | 内置发布 | 发布属 ⑤ MAP；职责分离，审批门才能统一 |
| **ADR-MME-08** | 素材**指纹去重 + 引用计数** | 每次重新下载 | 同源素材跨任务复用，省带宽与存储 |

## 10. 容量与性能估算

| 项 | 估算 |
|----|------|
| 单素材分析 | ASR：0.5–2× 实时（CPU Whisper）；LLM 分析：30–120s |
| 单变体渲染（60s 9:16） | 60–180s（无 GPU） |
| 典型矩阵规模 | 5 内容 × 3 画幅 × 2 Hook = **30 变体** |
| 全渲耗时（并发 2） | 30 × 120s / 2 ≈ **30 分钟** |
| 单变体存储 | 约 15–40MB（1080×1920，60s） |
| 单 VariantSet 存储 | 30 × 30MB ≈ **900MB** |
| 日产 VariantSet | 5–20 个 |

> ⚠️ **存储是 MME 的主要成本**。需配合 ⑤ MAP 的发布后清理策略与素材引用计数（FR-MIX-07）。

## 11. 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 渲染算力不足 | **高** | 高（矩阵规模放大） | 并发控制 + 先展开后渲染 + GPU 可选升级 |
| 存储成本失控 | 中 | 中 | 素材去重 + 引用计数 + 发布后清理策略 |
| 云 LLM 成本 | 中 | 中 | 四级缓存 + Ollama 降级 + 总量帽 |
| 剪映版本不兼容 | 中 | 中 | 标 `[待测]`；提供 ZIP 兜底 |
| 无 GPU reframe 质量差 | **高** | 中（体验） | 诚实标注；提供 16:9 直通选项 |
| 矩阵放大著作权风险 | 中 | **高** | 差异化检查 + 实质性转化质检 + Q1 拍板 |
| 渲染任务失败排查难 | 中 | 中 | 保留中间产物 + 可断点重试（NFR-MME-08） |

## 12. 与其他子系统的接口约定

| 对 | 约定 |
|----|------|
| ← **② TT** | 消费 `route=mme` 的 `TopicCandidate`；用 `material_refs` 取素材，`suggested_angles` 作为内容矩阵的输入 |
| ← **① IC** | 消费 `category=B_material` 的 `IntelItem`；`payload.media_refs` 中 `asset://` 可直接用，`https://` 需先下载 |

| ↔ **③ MIA** | **不直连**。MIA 是分析结论，MME 是可发布内容，二者不得混为同一按钮 |
