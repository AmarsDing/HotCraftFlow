# ⑤ MAP 媒体自动化发布矩阵系统 · 需求规格

> **子系统**：MAP · Media Auto-Publisher · 媒体自动化发布矩阵
> **版本**：v1.0 · **日期**：2026-10-17
> **上游**：PRD §7 · 契约 [`../00-shared/01-data-contract.md`](../00-shared/01-data-contract.md) §5
> **安全等级** 🔴：本子系统是**唯一能把内容发到公网**的出口，任何疏漏都不可逆

---

## 1. 目标与边界

| 项 | 内容 |
|----|------|
| **目标** | 把 `VariantSet` 按平台矩阵交叉分发到国内外媒体平台，经**强制审批门**、可排期、可审计，并把表现数据回流 |
| **输入** | `VariantSet`（来自 ④ MME） |
| **输出** | 各平台已发布内容 + 发布回执 + 表现数据回流 |
| **上游** | ④ MME |
| **下游** | ① IC / ② TT（表现数据回流） |

### 1.1 明确不做 🔴

| 不做 | 原因 |
|------|------|
| **不做无审批门的自动发布** | 「只接调度无审批门」**不算** FR-PUB-04 通过 |
| **不默认公开** | 所有路径默认 `private`/`unlisted`/平台草稿；**禁止**沿用 Open-Dispatch YouTube 默认 `public`（**NFR-17**） |
| **不承诺剪辑时间线画布** | 调研确认无 MIT 仓提供完整套件 |
| **不承诺全平台支持** | 视频号无开放发布 API，诚实标注「暂不支持」 |
| **不模拟用户操作绕过平台限制** | 平台 ToS；走官方开放平台（待决策 Q3） |
| **不做内容加工** | 加工是 ④ MME 的职责 |

## 4. 审批门（强制，不可绕过）🔴

沿用 `FR-M9-09` 的 **(A)+(B) 双层必须同过**：

```
(A) 调度适配器层  —— Open-Dispatch 契约或 Depend；CogSend（线程/重试/Insights）与
                     YominPost（改写+风控，MCP 故意无 publish）作厚调度 UX
(B) 审批门层      —— pendpost 范式：draft → approved/rejected + 禁自批 + publish 二次确认
```

### 4.1 四条铁律

| 规则 | 要求 |
|------|------|
| **默认私密** | 所有路径默认 `private`/`unlisted`/平台草稿；**禁止**默认 `public`（NFR-17） |
| **禁自批** | 提交者与审批者**不可为同一人/同一自动化身份** |
| **无门不公开** | 「只接调度无审批门」**不算** FR-PUB-04 通过 |
| **发布回执** | 记录 `post_id` / 时间 / 可见性 / 操作者，可审计 |

### 4.2 审批状态机

```
        ┌─────────┐   submit
        │  (新建)  │ ────────► ┌─────────┐
        └─────────┘            │  draft  │
                               └────┬────┘
                       ┌────────────┼────────────┐
                  approve       reject        （超时/撤回）
                       ▼            ▼            ▼
                ┌──────────┐  ┌──────────┐   ┌─────────┐
                │ approved │  │ rejected │   │  draft  │
                └────┬─────┘  └──────────┘   └─────────┘
                     │ publish（二次确认）
                     ▼
                ┌──────────┐
                │ published│ ← 记录回执
                └──────────┘
```

> **禁自批校验**：`approval.approver != submitter`，且 approver 不得为自动化身份。校验失败时**拒绝流转**。

## 5. 功能需求（FR-PUB-\*）

| ID | 名称 | 描述 | 验收标准 | 优先级 |
|----|------|------|----------|--------|
| **FR-PUB-01** | 适配器注册表 | 平台适配器可插拔，声明能力 | 新增平台不改核心；不支持时**明确报错** | **P1** |
| **FR-PUB-02** | 规格转码 | 按平台转分辨率/码率/时长/封面尺寸 | 失败**不阻断**草稿；规格表可配 | **P1** |
| **FR-PUB-03** | 文案按平台改写 | 按平台语气与长度限制改写 | 学 OD `/ai/adapt`；超长截断并提示 | **P1** |
| **FR-PUB-04** | 审批门 🔴 | draft → approve → publish + **禁自批** | 无 approve **不得** publish；可审计 | **P0** |
| **FR-PUB-05** | 账号池与隔离 🔴 | 多账号管理、**凭据加密**、账号-平台映射 | 本地加密（FR-M10-03）；账号可启停 | **P0** |
| **FR-PUB-06** | 排期与速率 | 定时发布 + 限流 + 重试/死信 | 区分**平台原生排期** vs **本机 worker 到点发** | **P1** |
| **FR-PUB-07** | 发布回执与审计 🔴 | `post_id`/时间/可见性/操作者落库 | 可导出审计日志 | **P0** |
| **FR-PUB-08** | 表现数据回流 | 播放/点赞/评论/完播 → 回灌 ② TT / ① IC | ≥1 平台打通；CSV 兜底 | **P2** |
| **FR-PUB-09** | 矩阵日历视图 | 账号 × 时间 × 平台排期总览 | 只读即可；**不承诺**剪辑画布 | **P2** |

**P0 共 3 条**（04/05/07），全部是**安全与合规**相关——这不是巧合。

## 6. 非功能需求（NFR）

| ID | 名称 | 要求 |
|----|------|------|
| **NFR-MAP-01** 🔴 | 默认私密 | 所有发布路径默认 `private`；改公开须填 `override_reason` + 审批 |
| **NFR-MAP-02** 🔴 | 禁自批 | 提交者与审批者不同；自动化身份不得审批 |
| **NFR-MAP-03** 🔴 | 凭据加密 | 账号凭据本地加密存储（FR-M10-03）；**日志脱敏** |
| **NFR-MAP-04** | 熔断 | 连续失败自动暂停账号/平台（见 §7） |
| **NFR-MAP-05** | 幂等 | 同一 `DispatchUnit` 重复提交不产生重复发布 |
| **NFR-MAP-06** | 总量上限 | 24h 发布总量硬上限，超限阻断需人工解除 |
| **NFR-MAP-07** | 审计 | 发布回执可导出；操作者、时间、可见性、post_id 全记录 |
| **NFR-MAP-08** | 隔离 | 账号池隔离：单账号异常不影响其他账号 |
| **NFR-MAP-09** | 可解释错误 | 平台返回错误须转译为可读提示（不暴露原始堆栈） |
| **NFR-MAP-10** | 降级 | 适配器不可用时，草稿保留可手动导出（ZIP 兜底） |

## 7. 熔断规则

| 触发条件 | 动作 |
|---------|------|
| 单账号连续 3 次发布失败 | 暂停该账号 30 分钟 + 告警 |
| 单平台 24h 内失败率 > 50% | 暂停该平台**全部**账号 + 人工介入 |
| 24h 发布总量超阈值 | 硬阻断，需人工解除 |
| 凭据失效 / 鉴权失败 | 立即停用账号，**不清凭据**（便于排查），标记待重新授权 |

## 8. 验收标准（子系统级）

| # | 验收项 | 判据 |
|---|-------|------|
| 1 | 审批门有效 | 构造「无 approve 直接 publish」请求，**必须失败** |
| 2 | 禁自批 | 同一用户提交并审批，**必须失败** |
| 3 | 默认私密 | 随机 20 次发布，可见性**全部**为 `private`/`unlisted`，无一为 `public` |
| 4 | 回执完整 | 随机 20 条回执，全部含 post_id / 时间 / 可见性 / 操作者 |
| 5 | 适配器可插拔 | 新增一个适配器（mock）**不改核心代码** |
| 6 | 熔断生效 | 人为注入连续失败，账号自动暂停且不影响其他账号 |
| 7 | 凭据安全 | 代码审计确认凭据加密存储；日志中**无**明文凭据 |
| 8 | 契约合规 | `DispatchUnit` 100% 通过 JSON Schema |

## 10. 诚实声明 🔴

1. **§3 是目标态不是已实现态**。国内平台适配器基本需自研；**视频号无开放发布 API**，V1 很可能不支持。
2. **公开发布不可逆**。一旦发出，撤回成本极高。这就是为什么审批门、默认私密、回执审计三项是 P0——它们不是流程负担，是**唯一的安全网**。
3. **不承诺「全平台一键发布」**。平台开放能力差异极大，诚实标注每个平台的实际能力边界比宣传全平台覆盖更重要。
4. **账号矩阵本身有平台 ToS 风险**。多账号发布可能违约，需走官方开放平台 + 克制规模（Q7）。
5. **数据回流能力取决于平台开放程度**。部分平台（小红书、视频号）回流能力弱或没有，V1 只承诺「≥1 平台打通」+ CSV 兜底。
