# ⑤ MAP 媒体自动化发布矩阵系统 · 概要设计

> **子系统**：MAP · **版本**：v1.0 · **日期**：2026-10-17
> **上游**：[`01-需求规格.md`](./01-需求规格.md) · PRD §7
> **详细设计**：[`03-详细设计.md`](./03-详细设计.md)
> **安全等级** 🔴：唯一对外出口，设计优先级为**安全 > 可审计 > 功能 > 体验**

---

## 1. 系统上下文

```
④ MME ──mm.mme.variant.ready.v1 (VariantSet)──►
                                                 ┌──────────────────────────────┐
                                                 │ ⑤ MAP 媒体自动化发布矩阵      │
                                                 │                              │
   用户（提交者）──create──►                      │  DispatchUnit 生成           │
   审核人（审批者）──approve──►                   │  ↓                           │
                                                 │  规格转码 → 文案改写         │
                                                 │  ↓                           │
                                                 │  ★ 审批门（禁自批）          │
                                                 │  ↓                           │
                                                 │  适配器矩阵 → 排期 → 发布    │
                                                 │  ↓                           │
                                                 │  回执 + 审计 + 表现回流      │
                                                 └───┬──────────────┬──────────┘
                                                     │              │
                                          各平台（12 个目标）   mm.map.feedback.v1
                                                                    ▼
                                                            ② TT / ① IC（回流）
```

**边界原则** 🔴

| 原则 | 说明 |
|------|------|
| **审批门不可绕过** | 所有发布路径**唯一**入口，无旁路 |
| **默认私密** | 发布的第一状态永远是 `private`，升公需显式审批 |
| **不加工只分发** | 内容加工属 ④ MME |
| **失败可降级** | 适配器不可用时保留草稿 + ZIP 手动导出兜底 |

## 2. 分层架构

```
┌─ L0 入口层  Intake ────────────────────────────────────────────┐
│  消费 VariantSet → 生成 DispatchUnit（默认 visibility=private） │
│  目标解析：`platform:slot` → PublishAccount                     │
└──────────────────────────┬────────────────────────────────────┘
                           ▼
┌─ L1 适配层  Adapt ─────────────────────────────────────────────┐
│  FR-PUB-02 规格转码（分辨率/码率/时长/封面）                     │
│  FR-PUB-03 文案按平台改写（学 OD /ai/adapt）                     │
│  **失败不阻断草稿**                                              │
└──────────────────────────┬────────────────────────────────────┘
                           ▼
┌─ L2 ★ 审批门层  ApprovalGate ──────────────────────────────────┐
│  draft → approved / rejected                                   │
│  🔴 禁自批：approver ≠ submitter，且非自动化身份                 │
│  🔴 无 approve 不得 publish                                     │
│  驳回**必须**填原因                                              │
└──────────────────────────┬────────────────────────────────────┘
                           ▼
┌─ L3 调度层  Schedule ──────────────────────────────────────────┐
│  双模式：① 平台原生排期（交给平台定时）                          │
│          ② 本机 worker 到点发（平台不支持排期时）                │
│  速率治理 + 熔断（NFR-MAP-04）                                  │
└──────────────────────────┬────────────────────────────────────┘
                           ▼
┌─ L4 发布层  Publish ───────────────────────────────────────────┐
│  适配器注册表（FR-PUB-01）：可插拔，声明能力                     │
│  账号池（FR-PUB-05）：凭据加密，账号隔离                         │
│  发布回执（FR-PUB-07）：post_id/时间/可见性/操作者               │
└──────────────────────────┬────────────────────────────────────┘
                           ▼
┌─ L5 回流与审计层  Feedback & Audit ─────────────────────────────┐
│  表现数据回流（FR-PUB-08）→ mm.map.feedback.v1                  │
│  审计日志导出 · 矩阵日历视图（FR-PUB-09）                        │
└────────────────────────────────────────────────────────────────┘
```

## 3. 关键设计：适配器注册表（FR-PUB-01）

### 3.1 能力声明模型

每个适配器**必须**声明自己的能力，不支持时**明确报错**而非静默失败：

```go
type Capability struct {
    Video         bool     // 支持视频
    ImageText     bool     // 支持图文
    NativeSchedule bool    // 支持平台原生排期
    DraftState    bool     // 支持草稿态
    Analytics     bool     // 支持数据回流
    MaxDurationSec int
    MaxSizeBytes   int64
    AspectRatios   []string   // ["9:16","1:1","16:9"]
    TitleMaxLen   int
    DescMaxLen    int
}
```

### 3.2 适配器接口

```go
type Publisher interface {
    PlatformKey() string                    // "douyin" / "youtube" ...，须与 VariantSet.copy 的键一致
    Capability() Capability
    Publish(ctx context.Context, u *DispatchUnit, acct *Account) (*Receipt, error)
    FetchAnalytics(ctx context.Context, acct *Account, postID string) (*Performance, error)
}
```

### 3.3 能力矩阵（目标态，非已实现）

| 平台 | 实现方式 | 说明 |
|------|---------|------|
| **YouTube** | Data API v3 | 官方 API 成熟，优先级最高 |
| **B站** | 开放平台 + Cookie | 有草稿态与回流，国内首选 |
| **X / Threads / LinkedIn** | 官方 API | 低难度 |
| **Reddit / Telegram** | 官方 API / Bot | 低难度 |
| **抖音 / 快手** | 开放平台（**需企业资质**） | 待 Q3 拍板 |
| **小红书** | 开放平台 | 风控严，难度高 |
| **知乎 / 头条 / 百家号** | 开放平台 | 中等 |
| **TikTok** | 官方 API（需资质） | 中等 |
| **Instagram Reels** | Graph API（需商务审核） | 难度高 |
| **视频号** | **无开放发布 API** | 诚实标注「暂不支持」 |

> 🔴 **诚实**：上表为**目标态**。国内平台适配器基本需自研，且多数需要企业资质。资质未到位前，这些平台在 UI 上标注「需资质」而非「可用」。

## 4. 关键设计：审批门（FR-PUB-04）🔴

### 4.1 双层模型

```
(A) 调度适配器层 —— 负责「怎么发」：线程/重试/Insights/规格适配
                    参考：Open-Dispatch（契约）、CogSend（重试/Insights）、YominPost（改写+风控）
(B) 审批门层     —— 负责「能不能发」：draft → approved + 禁自批 + publish 二次确认
                    参考：pendpost 范式

🔴 (A) 与 (B) 缺一不可。(A) 只是调度，(B) 才是安全网。
   「只接调度无审批门」不算 FR-PUB-04 通过。
```

> **选型说明**：YominPost 的 MCP **故意不提供 publish**——这个设计思路正合 (B) 层的定位，可作为审批门的 UX 参照。

### 4.2 状态机

```
        create
          ▼
    ┌───────────┐
    │   draft   │ ◄─────── 撤回 / 驳回后修改
    └─────┬─────┘
          │ approve（approver ≠ submitter）
          ▼
    ┌───────────┐
    │ approved  │
    └─────┬─────┘
          │ publish（二次确认 + 记录 operator）
          ▼
    ┌───────────┐
    │ published │
    └───────────┘

    旁支：draft --reject（须填 reason）--> rejected
```

### 4.3 三条校验（任一失败即拒绝）

| 校验 | 规则 |
|------|------|
| **状态校验** | `approval.state != approved` → 拒绝 publish |
| **禁自批校验** | `approval.approver == submitter` 或 approver 为自动化身份 → 拒绝 |
| **可见性校验** | `visibility.default != private` 且无 `override_reason` → 拒绝 |

### 4.4 二次确认

即使状态为 `approved`，实际 publish 操作仍需：
1. 显式调用 publish 接口（不与 approve 合并）
2. 记录 `publish.operator`（谁点的）
3. 若目标可见性非 private，需**额外**确认

> **理由**：approve 与 publish 分离，给「审批后反悔」留出最后一道人工闸门。

## 5. 关键设计：排期双模式（FR-PUB-06）

| 模式 | 适用 | 实现 | 优缺点 |
|------|------|------|--------|
| **① 平台原生排期** | 平台支持（YouTube/B站/微博/知乎等） | 调用平台 API 设置定时 | ✅ 不依赖本机在线；❌ 各平台 API 差异大 |
| **② 本机 worker 到点发** | 平台不支持排期 | asynq 定时任务，到点调 publish | ✅ 通用；❌ 需本机在线，错过时间点会延迟 |

**选择逻辑**

```
if adapter.Capability().NativeSchedule && 用户未强制本机:
    用模式 ①
else:
    用模式 ②
```

**UI 必须明示**当前用的是哪种模式——二者对「本机是否需要在线」的要求完全不同。

## 6. 关键设计：账号池与凭据（FR-PUB-05）🔴

### 6.1 账号模型

```
PublishChannel（平台渠道：douyin:main）
  └── PublishAccount × N（同一平台多个账号槽位）
        ├── credential_ref → 加密凭据
        ├── enabled
        ├── 健康状态（连续失败数 / 暂停至）
        └── 发布计数（24h 滚动）
```

> **账号-平台映射**：`DispatchUnit.targets` 中的 `platform:slot`（如 `douyin:a1`）解析到具体 `PublishAccount`。

### 6.2 凭据安全

| 措施 | 说明 |
|------|------|
| **加密存储** | 凭据本地加密（FR-M10-03 / 沿用 `pkg/crypto`），**不入库明文** |
| **日志脱敏** | 任何日志输出前脱敏 token / cookie / authorization |
| **内存最小化** | 凭据仅在发布时解密，用完即清 |
| **失效处理** | 鉴权失败立即停用账号，**不清凭据**（便于排查），标记待重新授权 |

### 6.3 账号隔离（NFR-MAP-08）

- 单账号熔断**不影响**其他账号
- 单平台熔断影响该平台全部账号（风控通常是平台级）
- V1 单平台 ≤3 账号（待决策 Q7）

## 8. 接口契约

### 8.1 NATS

| Subject | 载荷 | 方向 |
|---------|------|------|
| `mm.mme.variant.ready.v1` | `VariantSet` | ← MME |
| `mm.map.dispatch.v1` | `DispatchUnit` | 内部 |
| `mm.map.feedback.v1` | `PerformanceSnapshot` | → TT / IC |

### 8.2 REST（`api/media/v1/map`）

| 方法 | 路径 | 用途 |
|------|------|------|
| `GET/POST` | `/api/v1/media/map/channels` | 平台渠道列表/创建 |
| `GET/POST/PATCH` | `/api/v1/media/map/accounts` | 账号池管理（FR-PUB-05） |
| `POST` | `/api/v1/media/map/accounts/{id}/toggle` | 启停账号 |
| `POST` | `/api/v1/media/map/accounts/{id}/reauth` | 重新授权（凭据失效后） |
| `GET/POST` | `/api/v1/media/map/dispatch-units` | 分发单元列表/创建 |
| `GET` | `/api/v1/media/map/dispatch-units/{id}` | 详情（含审批状态与回执） |
| `POST` | `/api/v1/media/map/dispatch-units/{id}/submit` | 提交审批 |
| `POST` | `/api/v1/media/map/dispatch-units/{id}/approve` | ★ 审批（**禁自批**） |
| `POST` | `/api/v1/media/map/dispatch-units/{id}/reject` | 驳回（**须填原因**） |
| `POST` | `/api/v1/media/map/dispatch-units/{id}/publish` | ★ 发布（二次确认，须已 approved） |
| `POST` | `/api/v1/media/map/dispatch-units/{id}/cancel` | 撤回 |
| `GET` | `/api/v1/media/map/approvals` | 待审批队列 |
| `GET` | `/api/v1/media/map/receipts` | 发布回执与审计日志（可导出） |
| `GET` | `/api/v1/media/map/calendar` | 矩阵日历（FR-PUB-09） |
| `GET` | `/api/v1/media/map/analytics/{id}` | 表现数据（FR-PUB-08） |

### 8.3 前端页面（Quasar）

| 路由 | 页面 | 内容 |
|------|------|------|
| `/media/map/approvals` | **审批队列**（核心） | 待审卡片、预览、通过/驳回（填原因） |
| `/media/map/dispatch-units/{id}` | 分发详情 | 目标平台、审批状态、**发布回执**、表现数据 |
| `/media/map/accounts` | 账号池 | 账号列表、健康状态、启停、重新授权 |
| `/media/map/calendar` | 矩阵日历 | 账号 × 时间 × 平台总览（只读） |
| `/media/map/receipts` | 审计日志 | 回执列表、导出 |

**UI 强制要求** 🔴：
- 审批与发布**必须是两个独立操作**，不得合并为「一键发布」
- 可见性非 private 时**必须有醒目警示** + 二次确认弹窗
- 账号健康状态（暂停中/正常）必须可见

## 9. 关键技术决策（ADR 摘要）

| # | 决策 | 备选 | 理由 |
|---|------|------|------|
| **ADR-MAP-01** | 审批门 **(A)+(B) 双层缺一不可** | 只用调度层 | 「只接调度无审批门」= 违规内容直通公网 |
| **ADR-MAP-02** | **默认 private**，升公需显式审批 | 沿用 OD 默认 public | NFR-17；Open-Dispatch 默认 public 会直接炸 |
| **ADR-MAP-03** | approve 与 publish **分离** | 合并为一步 | 给「审批后反悔」留最后一道人工闸门 |
| **ADR-MAP-04** | **禁自批**硬校验 | 仅流程约定 | 流程约定会被绕过；硬校验才可靠 |
| **ADR-MAP-05** | 适配器**声明能力**，不支持明确报错 | 尽力而为静默降级 | 静默降级会让用户以为发了实际没发 |
| **ADR-MAP-06** | **抄 Open-Dispatch 契约自研**（Q10 建议） | Depend OD | OD 仅 ★17 个人维护；契约可抄，依赖不可靠 |
| **ADR-MAP-07** | 排期**双模式**并 UI 明示 | 统一本机到点发 | 平台原生排期不依赖本机在线，是更优解 |
| **ADR-MAP-08** | 熔断**账号级 + 平台级**双层 | 仅账号级 | 风控通常是平台级的 |
| **ADR-MAP-09** | 凭据**加密 + 日志脱敏 + 内存最小化** | 配置文件存放 | 凭据泄露 = 账号被盗用 |
| **ADR-MAP-10** | 视频号等无 API 平台**诚实标注不支持** | 模拟操作绕过 | 模拟操作违反平台 ToS（Q3） |
| **ADR-MAP-11** | 本机到点发 **operator 归属审批人（human）** | automation 身份直发 / 松开关 | 门写死拒绝 automation（不可关闭）与设计文档「worker 到点调 publish」冲突——裁决：审批即含「内容+可见性+目标+时间窗」完整授权，worker 只当时间触发器；门永不认 automation，红线不破。真相可查：worker 追加 reason="via=scheduler" 伴随审计，IP/UA 为空；confirm_public=true 视为审批人对可见性的既确认（2026-10-19 拍板） |

## 10. 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| **违规内容发到公网** | 中 | **极高**（不可逆） | 审批门 + 默认私密 + 禁自批（三重） |
| 平台资质未到位 | **高** | 高（国内平台不可用） | 提前申请；UI 标「需资质」；优先做 YouTube/B站等 |
| 账号被封 | 中 | 高 | 熔断 + 账号隔离 + 限流 + 规模克制（Q7） |
| 凭据泄露 | 低 | **极高** | 加密 + 脱敏 + 内存最小化 |
| 适配器被平台改版破坏 | **高** | 中 | 适配器隔离；失败明确报错；草稿保留 + ZIP 兜底 |
| 本机排期错过时间点 | 中 | 中 | 优先用平台原生排期；本机模式有补发与告警 |
| 发布总量失控 | 低 | 中 | 24h 硬上限 + 人工解除 |
| 数据回流能力弱 | **高** | 低 | V1 只承诺 ≥1 平台 + CSV 兜底 |
